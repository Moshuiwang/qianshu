# 产品文档：运营政策配置机器人

- **版本**：v0.1 草稿
- **更新日期**：2026-11-18
- **需求来源**：[会议记录 2026-11-18](会议记录/2026-11-18-运营政策配置流程.md)

---

## 1. 背景

各国运营每月通过邮件提交 30～50 条优惠政策申请，大促时更多（圣诞一次 100 条），全部由刘东升在明道云中手工录入。这项工作耗时，有时导致政策不能及时上线。

## 2. 目标

| 目标 | 衡量方式 |
|---|---|
| 替代人工录入 | 标准申请邮件由机器人自动建单，人工只处理异常 |
| 上线更及时 | 邮件到达后，几分钟内完成建单 |
| 节省人力 | 每月节省 ≥ 20 小时 |
| 不降低准确率 | 紫薇审批时的退回率不高于人工录入时 |

## 3. 已定的关键决策

| # | 决策 | 原因 |
|---|---|---|
| D1 | 申请入口**沿用邮件**，不改表单 | 申请人不需要学新东西，特殊需求可以直接写在邮件里 |
| D2 | 机器人**直接在明道云现有表单中新建单据**，不经飞书多维表格中转 | 明道云是正式记录系统，审批后自动同步 BOSS；加中转表会多一份需要保持一致的数据 |
| D3 | 产品形态是**飞书群机器人** | 团队日常在飞书沟通，汇报和纠错都在群里完成 |
| D4 | 机器人修改规则和代码**直接生效，不等人确认** | 用户决定。用自动测试、群内通知、一键回滚兜底 |
| D5 | **部署在用户自己的海外云服务器上**，AI 能力调用 Claude API | 机器人要 7×24 在线监听飞书消息、轮询邮箱，并能改自己的代码后重启；Claude 云端的定时任务按时间点启动，做不到常驻监听；Claude API 和海外服务在中国大陆服务器上无法访问 |
| D6 | 邮件来源用**网易企业邮箱原邮箱**，不用转发到 Gmail 的副本 | 网易是源头，少一个转发环节，转发失效时不会悄无声息地漏件；机器人也不接触用户的私人 Gmail |
| D7 | 机器人建单后**一并点击「提交申请」**，紫薇直接审批 | 用户决定，全自动 |
| D8 | 标签校验**先依靠明道云的报错**：标签填错时明道云会报错，机器人据此判断 | 用户决定；CRM 原始页面作为后备，需要时用户提供 |
| D9 | **群里所有人**都可以纠正机器人，纠正直接生效 | 用户决定；每次修改在群里通知、记录是谁提出的，可一键回滚 |
| D11 | 编码与运行先放在 **tzserver**（服务器上 tmux 中运行的 Claude 负责编码）；需要浏览器的调研和前期配置在本机完成 | 用户决定（2026-11-18） |
| D12 | 机器人汇报群为「**运营配置Agent**」（`.env` 中 `FEISHU_CHAT_ID` 对应的群，2026-11-18 接口核实）；所有时刻按 **UTC** 记录和汇报 | 用户确认：用户当前在 UTC+0 时区，与 tzserver 上其他项目一致 |
| D13 | 机器人用**产品负责人本人的明道云账号**登录 | 用户决定（2026-11-18）。机器人建的政策申请人都显示为该账号，审批通知、退回消息也发给该账号；汇报卡片注明「由千树Bot 代为提交」 |
| D10 | **完全复用明道云现有表单和按钮**：不改明道云任何配置、不向明道云管理员申请任何东西（包括开放接口密钥）。机器人用一个真实成员账号登录，发出与浏览器操作相同的请求 | 用户决定（2026-11-18）。代价见 10.3 |

## 4. 角色

| 角色 | 人 | 与机器人的关系 |
|---|---|---|
| 申请人 | 各国运营 | 发申请邮件；收到机器人的追问后补充信息 |
| 配置负责人 | 刘东升 | 群内看机器人汇报；处理异常；纠正机器人的错误 |
| 审批人 | 紫薇 | 在明道云审批机器人建的单据（流程不变） |
| 机器人 | — | 收件、建单、汇报、自我修正 |

## 5. 使用流程

```
申请邮件到达
   ↓
机器人读取邮件（自动监控邮箱，或群内 @机器人 发送）
   ↓
拆出政策字段（一封邮件可能有多条政策）
   ↓
在飞书知识库对应国家、年份下新建当天的存档页，粘贴申请明细（见 6.7）
   ↓
按规则逐条校验
   ├─ 通过 → 在明道云新建单据，「任务审批链接」填存档页链接，并提交申请
   └─ 不确定 → 不建单，记录原因
   ↓
在飞书群发处理结果卡片
   ↓
紫薇在明道云审批 → 自动同步 BOSS（现有流程）
```

## 6. 功能需求

### 6.1 收件

| 编号 | 需求 | 优先级 |
|---|---|---|
| F1.1 | 自动监控指定邮箱，识别政策申请邮件并处理 | P0 |
| F1.2 | 群内 @机器人，发送邮件正文或附件，机器人处理 | P0 |
| F1.3 | 同一封邮件不重复处理；需要重跑时，在群里明确说「重新处理」 | P0 |
| F1.4 | ~~支持把邮件转发或分享给机器人~~ | 不做：邮件在网易邮箱，机器人直接读取（D6） |

### 6.2 字段解析

申请邮件正文是**自由文字**，没有固定模板，每个人写法不同，需要由 AI 理解句意后拆字段。拆出的每个字段都要能在邮件原文中找到依据，找不到依据就按 R5 追问。

从邮件中识别以下字段，一条政策对应一条单据：

| 明道云字段 | 解析与填写规则 |
|---|---|
| 国家 | 识别国家名称，转换为国家编码 |
| 用户标签 | 识别标签名或编号，并在 CRM 中确认存在 |
| 是否维护互斥组 | 默认「是」 |
| 政策类型 | 按邮件内容判断，如「定向」 |
| 生效开始日期 | 取申请日期和今天中较晚的一个；超过当天 BOSS 配置截止时间则顺延一天 |
| 生效结束日期 | 取申请日期 |
| 优惠类型 | 如「充一送一 / 买一赠一」→「赠送」 |
| 是否限制降包用户 | 申请写「不限制升降包」→「否」 |
| 赠送节目包 | 选择对应节目包的附属包 copy，0 元计费 |
| 适用条件 | 按活动类型填写，如「休眠用户召回」 |
| 审批件 | 申请邮件截图 |

> 实际表结构见 10.4：节目包和用户标签是子表。字段 ID 与可选值在录制新建记录的请求时一并取得。

### 6.3 校验规则

| 编号 | 规则 | 不满足时 |
|---|---|---|
| R1 | 生效开始日期不早于今天 | 自动顺延，并在汇报中说明 |
| R2 | 标签有效（以明道云建单时是否报错为准，D8） | 不建单，汇报明道云的报错原文 |
| R3 | 影子标签类活动（需用户点确认）只能选一个标签 | 不建单，追问申请人 |
| R4 | 同一批政策中两条用户数相同，提示可能选重了标签 | 建单，汇报中标黄提醒 |
| R5 | 必填字段有缺失或理解不确定 | 不建单，追问申请人 |
| R6 | 赠送节目包能找到对应的附属包 | 不建单，汇报原因 |
| R7 | 「是否需要维护互斥组」只有邮件明确说明时才填「否」（选「否」会跳过配置直接生效） | 默认填「是」 |
| R8 | 定向政策必须有用户标签；政策结束日期不晚于标签最晚结束日期 | 不建单，追问申请人 |
| R9 | 必须能给出「任务审批链接」（网址）和「用户范围」 | 不建单，追问申请人 |
| R10 | 公司名称有多个匹配时（如赞比亚有两家），按邮件内容确定是哪一家 | 无法确定时不建单，追问 |

**原则：拿不准就不建。** 宁可多追问一次，也不建一条看起来正确、实际猜错了的单据，因为这类错误在审批时很难发现。

### 6.4 建单

| 编号 | 需求 | 优先级 |
|---|---|---|
| F4.1 | 用现有表单新建单据，并点击「提交申请」进入现有审批流程（D7、D10） | P0 |
| F4.2 | 单据上标记「机器人创建」，便于审批人识别和后续统计 | P0 |
| F4.3 | 同一封邮件的多条政策批量创建 | P0 |

### 6.5 群内汇报

每封邮件处理完，在群里发一张卡片，内容包括：

- 邮件来源：国家、申请人、邮件标题
- 已建单：条数，每条的明道云链接
- 自动调整：如「生效日期 16 号已顺延到 19 号」
- 未建单：哪几条、原因、需要谁补什么
- 提醒项：如 R4 疑似重复标签

### 6.7 申请存档到飞书知识库

会议中「把申请邮件存进归档目录，按国家、年份、操作日期归类，并把政策明细粘进去」，指的是**飞书知识库**「海外运营中心」，不是本地文件夹（会后核实，2026-11-18）。存档页的链接就是明道云必填字段「任务审批链接」的值。

| 项 | 规则 |
|---|---|
| 路径 | 运营中心主页 → 3. 用户运营部 → 2. 用户运营活动 → 4. 休眠用户召回活动 → 1. DVB休眠用户召回活动 → **大区** → **国家** → **「国家+休眠用户召回+年份」页** → **日期页** |
| 大区与国家 | 如「1. 东非英语区 → 4. 赞比亚」；另有西非英语区、西非法语区、中非法语区等。国家到大区的对应关系由机器人读目录得到 |
| 日期页 | 标题为操作日期 `YYYYMMDD`，如 `20261118`；同一国家同一天只建一页 |
| 页面内容 | 申请明细原文：活动周期、每个标签的用户数、政策内容、使用场景、标签名称 |
| 链接用途 | 该批所有政策的「任务审批链接」都填这一页的链接 |

真实样例：赞比亚 `20261118` 页（刘东升建）列了 6 个标签和政策，对应明道云里 6 条 `ZM_Dormant7_9M…_20261112` 记录，可作为第一组测试样例。

其他发现：明道云已有记录的「任务审批链接」绝大多数是知识库页面，少数是 Jira 工单（BOSSTODO-xxxx），什么情况下用 Jira 待确认。

### 6.6 自我修正

| 层级 | 触发 | 机器人的动作 | 防护 |
|---|---|---|---|
| 规则层（提示词、规则文件） | 群里有人指出错误，如「赞比亚 Basic 赠送包应该选 xxx」 | 修改规则，立即生效 | 群内通知改了什么、依据哪句话、影响哪类政策 |
| 代码层 | 程序报错，或规则层解决不了 | 调用 AI 编程工具修改代码 | 先跑历史样例测试，全部通过才部署；不通过就不上线并报告 |
| 兜底 | — | 每次修改保留版本 | 群里说「回滚」即退回上一版 |

## 8. 非功能需求

| 项 | 要求 |
|---|---|
| 运行方式 | 部署在用户的云服务器上，常驻运行；飞书用长连接模式接收消息，不需要公网地址和域名 |
| AI 调用 | 解析邮件、自我修正都调用 Claude API；服务器只负责收消息、存数据、调接口 |
| 代码管理 | 代码放在服务器的 git 仓库中，每次自我修改都是一次提交，回滚即退回上一次提交 |
| 响应时间 | 邮件到达到群内汇报，5 分钟以内 |
| 时区 | 日志、汇报卡片、存档页中的时刻一律写 UTC；知识库日期页标题（`YYYYMMDD`）按 UTC 日期 |
| 日志 | 记录每封邮件的处理过程：解析结果、校验结果、建单结果、错误信息，用于排查问题 |
| 密钥管理 | 飞书 App ID / Secret、明道云账号、网易邮箱授权码、Claude API Key 存放在服务器的配置文件中，不写进代码、不发到聊天里 |
| 权限 | 机器人使用的账号就是一个普通成员账号；程序只做新建记录和提交申请两类操作，不做审批、修改已提交的单据或删除 |

## 10. 技术调研结论（2026-11-18）

可信度：**确认**＝官方文档写明；**推断**＝文档未写，按上下文判断；**待实测**＝需要上线前在测试环境验证。

### 10.1 飞书机器人

| 能力 | 结论 | 可信度 |
|---|---|---|
| 长连接收消息 | 企业自建应用可用；官方 Python SDK `lark-oapi`；服务器只要能出公网，不需要公网 IP 和域名。每条事件需在 3 秒内响应，超时平台会重推，所以收到后先回执、再慢慢处理；可能重复推送，用 `message_id` 去重 | 确认 |
| 海外服务器 | 文档未提地区限制；飞书租户连 `open.feishu.cn`（国际版 Lark 连 `open.larksuite.com`，两者不通用） | 推断 |
| 群里能收到的消息 | 默认只收 @机器人 的消息（权限 `im:message.group_at_msg:readonly`）。收全部群消息需要敏感权限 `im:message.group_msg`，要企业管理员审批 | 确认 |
| 回复机器人卡片但不 @ | 文档未说明；判断只有 @ 权限时收不到 | 推断，待实测 |
| 卡片按钮回调 | 支持，走长连接，事件 `card.action.trigger`，3 秒内响应 | 确认 |
| 发送人身份 | 每条消息带发送人 `open_id`，可再查通讯录得到姓名，用于记录「谁提出的修改」（D9） | 确认 |

**对设计的影响**：群成员纠正机器人时需要 **@机器人**（例如在卡片下回复并 @），这样不用申请敏感权限。若希望不 @ 也能识别，需要管理员审批「获取群组中所有消息」权限，机器人会因此看到群里所有聊天内容。

### 10.2 网易企业邮箱

| 能力 | 结论 | 可信度 |
|---|---|---|
| 读信方式 | 只能走 IMAP；没有公开的读信 API | 确认 |
| IMAP 地址 | `imaphz.qiye.163.com`，SSL 端口 993 | 确认 |
| 登录凭据 | 用「客户端授权码」代替登录密码：网页版 设置 → 账户与安全 → 客户端设置，自己生成，只显示一次 | 确认 |
| IMAP 开关 | 管理员可按账号开关 IMAP；被关时报错 `LOGIN.PERMDENY` | 确认 |
| 海外 IP 登录 | 2026 年 1 月起，客户端协议在新设备登录命中风控会被拦截，需管理员在「安全中心 → 账号解禁」解除；管理员也可能设了「IP 登录管理」按地区限制 | 确认；是否会被拦截待实测 |

### 10.3 明道云：复用现有表单的实现方式（D10）

**原理**：在浏览器里每一次点击（新建记录、填字段、点「提交申请」），背后都是浏览器向明道云发出的一个网络请求。程序可以用同一个账号登录，发出同样的请求，效果与人工操作相同。Linux 服务器没有显示器，但这不影响：程序直接发请求不需要浏览器；需要浏览器的步骤（如登录页有脚本校验）可以用「无界面浏览器」在服务器上运行。

**两种做法，按优先级使用**

| 做法 | 怎么做 | 优点 | 缺点 |
|---|---|---|---|
| 1. 直接发请求（主路径） | 登录后拿到会话，直接调用浏览器背后的那些请求：新建记录、写子表、触发「提交申请」按钮 | 快；不受页面布局变化影响 | 这些请求是明道云内部使用的，没有官方文档，明道云升级时可能改变 |
| 2. 无界面浏览器模拟点击（后备） | 在服务器上运行无界面浏览器，像人一样打开表单、填写、点按钮 | 和人工操作完全一致 | 慢；页面改版就要改程序 |

**代价与风险**（这是不改明道云、不找管理员要付出的成本）

| 风险 | 说明 | 应对 |
|---|---|---|
| 用真人账号操作 | 记录的拥有者、操作日志都显示为这个账号（如你或刘东升）；账号密码或登录会话要放在服务器上 | 账号信息只放服务器 `.env`；汇报卡片中写明「由机器人代为提交」 |
| 登录可能被拦 | 海外服务器首次登录，明道云可能要求验证码或提示异地登录 | 首次登录由人工在服务器上完成一次；会话过期时机器人在群里提醒 |
| 内部请求会变 | 明道云升级后请求格式可能变化，导致建单失败 | 建单失败立即在群里报告，并触发自我修复（D4）；无法自动修复时改用做法 2 |
| 平台规则 | 非官方的自动化方式，明道云不提供支持 | 控制频率（每条间隔数秒），不做批量抓取 |

**录制结果（2026-11-18）**：用户授权后，Claude 在已登录的浏览器里新建了一条「【测试】」开头的政策记录并点击了「提交申请」，同时记录了网络请求。字段 ID、选项 ID 等内部标识保存在本机私有文件 `.private/`（不进仓库）。

| 操作 | 录到的请求 | 结论 |
|---|---|---|
| 新建记录 | 一个「新增记录」请求，带 55 个字段 | 人工只填约 17 个字段，其余约 38 个由**页面在浏览器里自动计算带出**：申请人、审批人、配置人、通知人群、公司 ID、BOSS 接口字段一组、同期有效政策列表、标签汇总、节目包价格等 |
| 提交申请 | 一个「启动流程」请求，参数是表 ID、记录 ID 列表、按钮 ID | 很简单；记录 ID 是列表，一次可提交多条；提交后状态从「新建」变为「待审批」 |
| 登录 | 未录（录制会打断当前登录） | 待在服务器上首次登录时确认 |

**据此调整做法**：

- **新建记录用无界面浏览器填表（做法 2）**。原因：那约 38 个自动带出的字段是页面脚本根据表单配置算出来的，其中「同期有效政策」「节目包价格」需要实时查询。程序直接发请求就得自己重算这些字段，一旦明道云里的表单配置调整，程序算出的值就会和页面不一致，而且不会报错，BOSS 同步时才会出问题。让浏览器真实填表，这些字段由页面自己算，最不容易出错。
- **提交申请直接发请求（做法 1）**。它只需要记录 ID 和按钮 ID，不涉及自动计算。
- **「提交申请」按钮只对申请人本人显示**：申请人字段默认是登录人，所以机器人用谁的账号登录，谁就是这些政策的申请人。

**已调研但不采用的方案**：明道云官方开放接口（需要应用管理员生成 AppKey / Sign）、为按钮新增「字段变化触发」或「Webhook 触发」的流程（需要管理员改配置）。这些都需要改明道云或找管理员，与 D10 冲突。官方接口也不能触发自定义按钮。

来源（官方接口部分）：
- https://help.mingdao.com/api/introduction
- https://help.mingdao.com/custom-action/introduction/

### 10.6 明道云审批流程与状态跟踪（2026-11-18 页面观察）

**视图与当时的记录数**：新建 31｜待审批 0｜待配置 0｜配置完成 3047｜生效政策 102｜BOSS 创建完成待上架 2｜BOSS 操作失败 0。

**流程**（从「流程待办 → 抄送」里的通知还原）：

```
新建 ──提交申请──▶ 待审批 ──审批人通过──▶ 待配置 ──配置人在 BOSS 配置──▶ 配置完成 ──▶ 生效政策
                     │                        │
                     └─审批人退回──▶ 回到新建   └─配置人「退回修改」──▶ 回到新建
                                                                   另有：BOSS 创建完成待上架 / BOSS 操作失败
```

| 通知标题 | 含义 | 例子 |
|---|---|---|
| DVB政策审批通过 | 审批人通过，进入待配置 | 「审批政策通过待配置：加纳-升级权益-充30送30-2026-11-18-00002077」 |
| DVB政策退回申请 | 审批人退回，回到新建 | 2026-11-18 赞比亚 ZM_Dormant7 那 6 条被审批人退回 |
| DVB政策重新修改 | 审批通过后，配置人退回要求修改 | 「退回政策修改：加纳-…-00002078」 |
| DVB政策新建/更改优惠政策->BOSS接口参数生成 | 新建或修改政策时自动运行的工作流 | 见下方「副作用」 |

每条通知带一个**政策编号**：`国家-优惠类型-优惠内容-生效日期-流水号`，如 `赞比亚-赠送时长-充30送30-2026-11-19-00002081`。

**机器人可以增加的跟踪**（建议进第一期）：

| 跟踪点 | 机器人动作 |
|---|---|
| 提交后长时间停在「待审批」 | 每天汇总一次未处理的申请，提醒审批人 |
| 审批人「退回申请」 | 在群里说明哪几条被退回、退回原因，追问申请人或按意见修改后重新提交 |
| 配置人「退回修改」 | 同上 |
| 进入「BOSS 操作失败」 | 立即在群里报警 |
| 进入「生效政策」 | 在原汇报卡片上标记「已生效」，形成从邮件到生效的闭环 |

实现方式待定：读取机器人账号的「流程待办 → 抄送」通知，或定时查询机器人所建记录的「政策状态」。当前账号**没有权限查看工作流运行详情**（点开报「工作表字段权限错误」），所以只能看状态、看不到每一步的细节。

**副作用：新建一条政策会连带重算同国家的其他政策**

2026-11-18 21:28 新建测试记录时，工作流「新建/更改优惠政策->BOSS接口参数生成」以申请人身份运行了 **20 次**：测试记录 1 条，加上 19 条赞比亚的真实政策（ZM_Dormant7…、ZM_Xmas2026…、ZM_AR_20260907 等）。推测是新政策进入了同国家的「同期有效优惠政策」，触发相关政策重新生成 BOSS 接口参数。具体改了哪些字段，因权限所限**未知**。

由此带来两条约束：
1. **不能随手在正式表里建测试记录。** 测试会牵动真实政策。后续测试要么事先和审批人、配置人约好，要么只做「填表不保存」的演练。
2. 机器人每建一条政策，都会触发同国家其他政策的重算。这是现有系统的正常行为，人工建单时也一样，但机器人批量建单时要控制节奏。

**测试记录的去向**：`【测试】qianshu_ZM_test_20261118` 已不在任何视图中，按记录 ID 打开也无法显示，推测已被删除，删除人未知。

### 10.4 明道云「优惠政策申请」表的实际结构（2026-11-18 页面观察）

在已登录的浏览器中打开一条记录看到的结构，只读未改。字段 ID、类型、可选值在录制新建记录的请求时确认（10.3）。

**视图（即政策状态的流转）**：新建 → 待审批 → 待配置 → 配置完成 → 生效政策；另有「BOSS 创建完成待上架」「BOSS 操作失败」。机器人建的单据停在「新建（运营中心）」，提交后进入「待审批」。

**记录上的按钮**：每条记录顶部有「提交申请」按钮；列表页可勾选多条后提交，每条记录各发起一个审批（用户确认）。

**字段**

| 分组 | 字段 | 说明 |
|---|---|---|
| 顶部 | 优惠政策名称 | 命名规则形如 `国家代码_活动_套餐_日期`，如 `ZM_Dormant7_9MDTHsuper_20261112`（ZM＝赞比亚）。命名规则需向刘东升确认 |
| | 是否需要维护互斥组 | 是／否。选「否」时政策自动创建并上架、直接生效；表单提示「需要互斥组的情况不要选否」 |
| | 政策状态 | 如「新建（运营中心）」 |
| 基本信息 | 公司名称 | 国家，如赞比亚 |
| | 政策类型 | 如「定向政策」 |
| | 开始日期、结束日期 | |
| | 优惠方式、优惠类型 | 如「赠送时长」 |
| | 是否只触发一次 | 是／否 |
| | 降包用户取消优惠 | 是／否（对应会议中的「是否限制降包用户」） |
| 优惠信息 | 充值天数、赠送天数 | 如充 30 送 30 |
| | 多买多送 | 是／否 |
| | 生效倍数 | 数字 |
| 节目包（子表） | 当前节目包、当前节目包价格计划、赠送节目包 | 一条政策可含多行；赠送节目包为 `原包名_copy` 的附属包价格计划 |
| 用户标签（子表） | 标签名称、处理成功用户数 | 影子标签名为原标签名加 `_image` 后缀 |
| 标签汇总 | 标签与适用条件关系、标签总用户数、目标标签数量、标签最早开始日期、标签最晚结束日期 | 多为根据子表自动计算，机器人应无需填写（待确认） |
| 其他页签 | 适用条件、审批件、辅助字段、BOSS 接口字段 | 内容待拿到表结构后确认；「BOSS 接口字段」可能由系统生成 |

**录制中发现的表单规则**（机器人建单前就要满足，否则页面不让保存）

| 规则 | 表单提示 |
|---|---|
| 政策类型选「定向政策」时必须选用户标签 | 政策类型与用户标签配置不一致 |
| 政策结束日期不能晚于所选标签的最晚结束日期 | 标签结束日期早于政策结束日期 |
| 「适用条件」页签的「用户范围」必填（自由文本，如「休眠用户召回」） | 请填写用户范围 |
| 「审批件」页签的「任务审批链接」必填，且必须是网址；审批件附件不是必填 | Please enter Link |
| 选「赠送时长」后，「获得优惠后不允许换包」「优惠后是否升包」会隐藏 | — |
| 节目包子表：选了当前节目包后价格计划自动带出；「优惠结束后」不可编辑 | — |
| 搜索公司「赞比亚」会出现两家公司（Zambia Corp. 与 Pamodzi 公司），需按邮件判断 | — |
| 审批人、配置人、通知人群由表单默认带出，不需要填 | — |

**对设计的影响**

- 6.2 的字段表需按上表重写：节目包、用户标签是**子表**，一条政策可带多行，机器人建单时要同时写子表。
- 「是否需要维护互斥组」选错的后果严重（选「否」会直接生效），机器人默认填「是」，邮件里没有明确说明时不得填「否」。
- 机器人运行在 Linux 服务器上，按 10.3 的做法 1 直接发请求操作现有表单，必要时用无界面浏览器（做法 2）。
