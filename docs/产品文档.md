# 产品文档：运营政策配置机器人

- **版本**：v0.1 草稿
- **更新日期**：2026-11-18
- **需求来源**：[会议记录 2026-11-18](会议记录/2026-11-18-运营政策配置流程.md)

---

## 1. 背景

各国运营每月通过邮件提交 30～50 条优惠政策申请，大促时更多（圣诞一次 100 条），全部由刘东升在明道云中手工录入。这项工作耗时，有时导致政策不能及时上线。

## 2. 目标

| 目标 | 衡量方式 |
|---|---|
| 替代人工录入 | 标准申请邮件由机器人自动建单，人工只处理异常 |
| 上线更及时 | 邮件到达后，几分钟内完成建单 |
| 节省人力 | 每月节省 ≥ 20 小时 |
| 不降低准确率 | 紫薇审批时的退回率不高于人工录入时 |

## 3. 已定的关键决策

| # | 决策 | 原因 |
|---|---|---|
| D1 | 申请入口**沿用邮件**，不改表单 | 申请人不需要学新东西，特殊需求可以直接写在邮件里 |
| D2 | 机器人**直接新建明道云单据**，不经飞书多维表格中转 | 明道云是正式记录系统，审批后自动同步 BOSS；加中转表会多一份需要保持一致的数据 |
| D3 | 产品形态是**飞书群机器人** | 团队日常在飞书沟通，汇报和纠错都在群里完成 |
| D4 | 机器人修改规则和代码**直接生效，不等人确认** | 用户决定。用自动测试、群内通知、一键回滚兜底 |
| D5 | **部署在用户自己的海外云服务器上**，AI 能力调用 Claude API | 机器人要 7×24 在线监听飞书消息、轮询邮箱，并能改自己的代码后重启；Claude 云端的定时任务按时间点启动，做不到常驻监听；Claude API 和海外服务在中国大陆服务器上无法访问 |
| D6 | 邮件来源用**网易企业邮箱原邮箱**，不用转发到 Gmail 的副本 | 网易是源头，少一个转发环节，转发失效时不会悄无声息地漏件；机器人也不接触用户的私人 Gmail |
| D7 | 机器人建单后**一并完成「勾选并提交申请」**，紫薇直接审批 | 用户决定，全自动。按钮没有接口，需明道云管理员新增一个由字段变化触发的提交流程，见 10.3 |
| D8 | 标签校验**先依靠明道云的报错**：标签填错时明道云会报错，机器人据此判断 | 用户决定；CRM 原始页面作为后备，需要时用户提供 |
| D9 | **群里所有人**都可以纠正机器人，纠正直接生效 | 用户决定；每次修改在群里通知、记录是谁提出的，可一键回滚 |

## 4. 角色

| 角色 | 人 | 与机器人的关系 |
|---|---|---|
| 申请人 | 各国运营 | 发申请邮件；收到机器人的追问后补充信息 |
| 配置负责人 | 刘东升 | 群内看机器人汇报；处理异常；纠正机器人的错误 |
| 审批人 | 紫薇 | 在明道云审批机器人建的单据（流程不变） |
| 机器人 | — | 收件、建单、汇报、自我修正 |

## 5. 使用流程

```
申请邮件到达
   ↓
机器人读取邮件（自动监控邮箱，或群内 @机器人 发送）
   ↓
拆出政策字段（一封邮件可能有多条政策）
   ↓
按规则逐条校验
   ├─ 通过 → 在明道云新建单据，附邮件截图
   └─ 不确定 → 不建单，记录原因
   ↓
在飞书群发处理结果卡片
   ↓
紫薇在明道云审批 → 自动同步 BOSS（现有流程）
```

## 6. 功能需求

### 6.1 收件

| 编号 | 需求 | 优先级 |
|---|---|---|
| F1.1 | 自动监控指定邮箱，识别政策申请邮件并处理 | P0 |
| F1.2 | 群内 @机器人，发送邮件正文或附件，机器人处理 | P0 |
| F1.3 | 同一封邮件不重复处理；需要重跑时，在群里明确说「重新处理」 | P0 |
| F1.4 | ~~支持把邮件转发或分享给机器人~~ | 不做：邮件在网易邮箱，机器人直接读取（D6） |

### 6.2 字段解析

申请邮件正文是**自由文字**，没有固定模板，每个人写法不同，需要由 AI 理解句意后拆字段。拆出的每个字段都要能在邮件原文中找到依据，找不到依据就按 R5 追问。

从邮件中识别以下字段，一条政策对应一条单据：

| 明道云字段 | 解析与填写规则 |
|---|---|
| 国家 | 识别国家名称，转换为国家编码 |
| 用户标签 | 识别标签名或编号，并在 CRM 中确认存在 |
| 是否维护互斥组 | 默认「是」 |
| 政策类型 | 按邮件内容判断，如「定向」 |
| 生效开始日期 | 取申请日期和今天中较晚的一个；超过当天 BOSS 配置截止时间则顺延一天 |
| 生效结束日期 | 取申请日期 |
| 优惠类型 | 如「充一送一 / 买一赠一」→「赠送」 |
| 是否限制降包用户 | 申请写「不限制升降包」→「否」 |
| 赠送节目包 | 选择对应节目包的附属包 copy，0 元计费 |
| 适用条件 | 按活动类型填写，如「休眠用户召回」 |
| 审批件 | 申请邮件截图 |

> 实际表结构见 10.4：节目包和用户标签是子表。字段 ID 与可选值待拿到 API 密钥后用接口读取。

### 6.3 校验规则

| 编号 | 规则 | 不满足时 |
|---|---|---|
| R1 | 生效开始日期不早于今天 | 自动顺延，并在汇报中说明 |
| R2 | 标签有效（以明道云建单时是否报错为准，D8） | 不建单，汇报明道云的报错原文 |
| R3 | 影子标签类活动（需用户点确认）只能选一个标签 | 不建单，追问申请人 |
| R4 | 同一批政策中两条用户数相同，提示可能选重了标签 | 建单，汇报中标黄提醒 |
| R5 | 必填字段有缺失或理解不确定 | 不建单，追问申请人 |
| R6 | 赠送节目包能找到对应的附属包 | 不建单，汇报原因 |
| R7 | 「是否需要维护互斥组」只有邮件明确说明时才填「否」（选「否」会跳过配置直接生效） | 默认填「是」 |

**原则：拿不准就不建。** 宁可多追问一次，也不建一条看起来正确、实际猜错了的单据，因为这类错误在审批时很难发现。

### 6.4 建单

| 编号 | 需求 | 优先级 |
|---|---|---|
| F4.1 | 通过明道云接口新建单据，进入现有审批流程 | P0 |
| F4.2 | 单据上标记「机器人创建」，便于审批人识别和后续统计 | P0 |
| F4.3 | 同一封邮件的多条政策批量创建 | P0 |

### 6.5 群内汇报

每封邮件处理完，在群里发一张卡片，内容包括：

- 邮件来源：国家、申请人、邮件标题
- 已建单：条数，每条的明道云链接
- 自动调整：如「生效日期 16 号已顺延到 19 号」
- 未建单：哪几条、原因、需要谁补什么
- 提醒项：如 R4 疑似重复标签

### 6.6 自我修正

| 层级 | 触发 | 机器人的动作 | 防护 |
|---|---|---|---|
| 规则层（提示词、规则文件） | 群里有人指出错误，如「赞比亚 Basic 赠送包应该选 xxx」 | 修改规则，立即生效 | 群内通知改了什么、依据哪句话、影响哪类政策 |
| 代码层 | 程序报错，或规则层解决不了 | 调用 AI 编程工具修改代码 | 先跑历史样例测试，全部通过才部署；不通过就不上线并报告 |
| 兜底 | — | 每次修改保留版本 | 群里说「回滚」即退回上一版 |

## 7. 不在第一期范围

- BOSS 中的政策优先级配置（另一个系统，需先确认是否有接口）
- 改用表单收集申请
- 邮件的存档整理（原来按大区 / 国家 / 日期存放的目录）

## 8. 非功能需求

| 项 | 要求 |
|---|---|
| 运行方式 | 部署在用户的云服务器上，常驻运行；飞书用长连接模式接收消息，不需要公网地址和域名 |
| AI 调用 | 解析邮件、自我修正都调用 Claude API；服务器只负责收消息、存数据、调接口 |
| 代码管理 | 代码放在服务器的 git 仓库中，每次自我修改都是一次提交，回滚即退回上一次提交 |
| 响应时间 | 邮件到达到群内汇报，5 分钟以内 |
| 日志 | 记录每封邮件的处理过程：解析结果、校验结果、建单结果、错误信息，用于排查问题 |
| 密钥管理 | 飞书 App ID / Secret、明道云 AppKey / Sign 存放在运行机器的配置文件中，不写进代码、不发到聊天里 |
| 权限 | 机器人只有明道云政策表的新建权限，没有审批和删除权限 |

## 10. 技术调研结论（2026-11-18）

可信度：**确认**＝官方文档写明；**推断**＝文档未写，按上下文判断；**待实测**＝需要上线前在测试环境验证。

### 10.1 飞书机器人

| 能力 | 结论 | 可信度 |
|---|---|---|
| 长连接收消息 | 企业自建应用可用；官方 Python SDK `lark-oapi`；服务器只要能出公网，不需要公网 IP 和域名。每条事件需在 3 秒内响应，超时平台会重推，所以收到后先回执、再慢慢处理；可能重复推送，用 `message_id` 去重 | 确认 |
| 海外服务器 | 文档未提地区限制；飞书租户连 `open.feishu.cn`（国际版 Lark 连 `open.larksuite.com`，两者不通用） | 推断 |
| 群里能收到的消息 | 默认只收 @机器人 的消息（权限 `im:message.group_at_msg:readonly`）。收全部群消息需要敏感权限 `im:message.group_msg`，要企业管理员审批 | 确认 |
| 回复机器人卡片但不 @ | 文档未说明；判断只有 @ 权限时收不到 | 推断，待实测 |
| 卡片按钮回调 | 支持，走长连接，事件 `card.action.trigger`，3 秒内响应 | 确认 |
| 发送人身份 | 每条消息带发送人 `open_id`，可再查通讯录得到姓名，用于记录「谁提出的修改」（D9） | 确认 |

**对设计的影响**：群成员纠正机器人时需要 **@机器人**（例如在卡片下回复并 @），这样不用申请敏感权限。若希望不 @ 也能识别，需要管理员审批「获取群组中所有消息」权限，机器人会因此看到群里所有聊天内容。

| 能力 | 结论 | 可信度 |
|---|---|---|
| 读信方式 | 只能走 IMAP；没有公开的读信 API | 确认 |
| IMAP 地址 | `imaphz.qiye.163.com`，SSL 端口 993 | 确认 |
| 登录凭据 | 用「客户端授权码」代替登录密码：网页版 设置 → 账户与安全 → 客户端设置，自己生成，只显示一次 | 确认 |

### 10.3 明道云开放接口

| 能力 | 结论 | 可信度 |
|---|---|---|
| 鉴权 | AppKey + Sign，在应用的「授权管理 → 新建授权密钥」生成，只有应用管理员能看到这个页面。密钥身份是**应用管理员级别**；能否限制成只读、某张表或仅新建，文档没写 | 确认；权限范围未知 |
| 读表结构 | `GET /v3/app/worksheets/{worksheet_id}` 返回字段列表 | 确认 |
| 新建记录 | 单条 `POST /v3/app/worksheets/{id}/rows`，批量 `.../rows/batch`；参数 `triggerWorkflow` 控制是否触发工作流，默认值待实测 | 确认 |
| 字段值错误 | 返回 `error_code` / `error_msg`，如 10002 参数值错误、10007 数据不存在、430019 必填为空、430021 不满足业务规则。标签填错时是报错还是被静默忽略，**待实测**（影响 D8） | 错误码确认；行为待实测 |
| 点击自定义按钮 | **没有接口**。按钮只能由人点击 | 确认 |
| 发起审批 | 审批是工作流里的一个节点，没有「为某条记录发起审批」的接口；只要能触发工作流，就能发起审批 | 确认 |
| 限流 | 按调用方 IP，新增、修改记录等接口每个 IP 每秒 50 次；超限返回 503，建议间隔约 200ms 重试 | 确认 |

**D7 的实现方式：由明道云管理员新增一个能被接口触发的提交流程**，复用现有流程里的审批节点。两种做法：

| 做法 | 怎么触发 | 对紫薇的影响 |
|---|---|---|
| A. Webhook 触发的流程 | 机器人建完一批单据后，调用流程的 Webhook 地址，传入记录 | 与现状一致，但管理员要额外管理一个触发地址和它的密钥 |
| B. 字段变化触发的流程（推荐） | 新增字段「机器人提交」，机器人建单后把它改为「是」，流程随之启动 | 每条记录一个审批，与现状一致；配置最简单 |

用户确认（2026-11-18）：现在勾选多条后点「提交申请」，**每条记录各发起一个审批**。做法 B 与现状一致且配置最简单，所以推荐 B。现有的人工按钮保留不动，作为备用。

**安全提示**：密钥是应用管理员级别，接口层面能做的事比「新建」多。约束靠代码和审核规则保证：机器人只调用读表结构、新建记录、触发提交流程这三类接口（见 AGENTS.md 审核规则）。

### 10.4 明道云「优惠政策申请」表的实际结构（2026-11-18 页面观察）

在已登录的浏览器中打开一条记录看到的结构，只读未改。字段 ID、类型、可选值需要拿到 API 密钥后用「读表结构」接口确认。

**视图（即政策状态的流转）**：新建 → 待审批 → 待配置 → 配置完成 → 生效政策；另有「BOSS 创建完成待上架」「BOSS 操作失败」。机器人建的单据停在「新建（运营中心）」，提交后进入「待审批」。

**记录上的按钮**：每条记录顶部有「提交申请」按钮；列表页可勾选多条后提交，每条记录各发起一个审批（用户确认）。

**字段**

| 分组 | 字段 | 说明 |
|---|---|---|
| 顶部 | 优惠政策名称 | 命名规则形如 `国家代码_活动_套餐_日期`，如 `ZM_Dormant7_9MDTHsuper_20261112`（ZM＝赞比亚）。命名规则需向刘东升确认 |
| | 是否需要维护互斥组 | 是／否。选「否」时政策自动创建并上架、直接生效；表单提示「需要互斥组的情况不要选否」 |
| | 政策状态 | 如「新建（运营中心）」 |
| 基本信息 | 公司名称 | 国家，如赞比亚 |
| | 政策类型 | 如「定向政策」 |
| | 开始日期、结束日期 | |

**对设计的影响**

- 6.2 的字段表需按上表重写：节目包、用户标签是**子表**，一条政策可带多行，机器人建单时要同时写子表。
- 「是否需要维护互斥组」选错的后果严重（选「否」会直接生效），机器人默认填「是」，邮件里没有明确说明时不得填「否」。
- 机器人程序将运行在没有浏览器的 Linux 服务器上，**只通过开放接口操作明道云**，不使用浏览器脚本。
