# 产品文档：运营政策配置机器人

- **版本**：v0.1 草稿
- **更新日期**：2026-11-18
- **需求来源**：[会议记录 2026-11-18](会议记录/2026-11-18-运营政策配置流程.md)

---

## 1. 背景

各国运营每月通过邮件提交 30～50 条优惠政策申请，大促时更多（圣诞一次 100 条），全部由刘东升在明道云中手工录入。这项工作耗时，有时导致政策不能及时上线。

## 2. 目标

| 目标 | 衡量方式 |
|---|---|
| 替代人工录入 | 标准申请邮件由机器人自动建单，人工只处理异常 |
| 上线更及时 | 邮件到达后，几分钟内完成建单 |
| 节省人力 | 每月节省 ≥ 20 小时 |
| 不降低准确率 | 紫薇审批时的退回率不高于人工录入时 |

## 3. 已定的关键决策

| # | 决策 | 原因 |
|---|---|---|
| D1 | 申请入口**沿用邮件**，不改表单 | 申请人不需要学新东西，特殊需求可以直接写在邮件里 |
| D2 | 机器人**直接新建明道云单据**，不经飞书多维表格中转 | 明道云是正式记录系统，审批后自动同步 BOSS；加中转表会多一份需要保持一致的数据 |
| D3 | 产品形态是**飞书群机器人** | 团队日常在飞书沟通，汇报和纠错都在群里完成 |
| D4 | 机器人修改规则和代码**直接生效，不等人确认** | 用户决定。用自动测试、群内通知、一键回滚兜底 |
| D5 | **部署在用户自己的云服务器上**，AI 能力调用 Claude API | 机器人要 7×24 在线监听飞书消息、轮询邮箱，并能改自己的代码后重启；Claude 云端的定时任务按时间点启动，做不到常驻监听 |

## 4. 角色

| 角色 | 人 | 与机器人的关系 |
|---|---|---|
| 申请人 | 各国运营 | 发申请邮件；收到机器人的追问后补充信息 |
| 配置负责人 | 刘东升 | 群内看机器人汇报；处理异常；纠正机器人的错误 |
| 审批人 | 紫薇 | 在明道云审批机器人建的单据（流程不变） |
| 机器人 | — | 收件、建单、汇报、自我修正 |

## 5. 使用流程

```
申请邮件到达
   ↓
机器人读取邮件（自动监控邮箱，或群内 @机器人 发送）
   ↓
拆出政策字段（一封邮件可能有多条政策）
   ↓
按规则逐条校验
   ├─ 通过 → 在明道云新建单据，附邮件截图
   └─ 不确定 → 不建单，记录原因
   ↓
在飞书群发处理结果卡片
   ↓
紫薇在明道云审批 → 自动同步 BOSS（现有流程）
```

## 6. 功能需求

### 6.1 收件

| 编号 | 需求 | 优先级 |
|---|---|---|
| F1.1 | 自动监控指定邮箱，识别政策申请邮件并处理 | P0 |
| F1.2 | 群内 @机器人，发送邮件正文或附件，机器人处理 | P0 |
| F1.3 | 同一封邮件不重复处理；需要重跑时，在群里明确说「重新处理」 | P0 |
| F1.4 | 支持把邮件转发或分享给机器人 | P1，取决于邮箱类型，需实测 |

### 6.2 字段解析

从邮件中识别以下字段，一条政策对应一条单据：

| 明道云字段 | 解析与填写规则 |
|---|---|
| 国家 | 识别国家名称，转换为国家编码 |
| 用户标签 | 识别标签名或编号，并在 CRM 中确认存在 |
| 是否维护互斥组 | 默认「是」 |
| 政策类型 | 按邮件内容判断，如「定向」 |
| 生效开始日期 | 取申请日期和今天中较晚的一个；超过当天 BOSS 配置截止时间则顺延一天 |
| 生效结束日期 | 取申请日期 |
| 优惠类型 | 如「充一送一 / 买一赠一」→「赠送」 |
| 是否限制降包用户 | 申请写「不限制升降包」→「否」 |
| 赠送节目包 | 选择对应节目包的附属包 copy，0 元计费 |
| 适用条件 | 按活动类型填写，如「休眠用户召回」 |
| 审批件 | 申请邮件截图 |

> 待补：明道云表的完整字段清单、每个字段的可选值。需要登录明道云或通过 API 读取表结构后补充。

### 6.3 校验规则

| 编号 | 规则 | 不满足时 |
|---|---|---|
| R1 | 生效开始日期不早于今天 | 自动顺延，并在汇报中说明 |
| R2 | 标签在 CRM 中存在且有用户 | 不建单，汇报原因 |
| R3 | 影子标签类活动（需用户点确认）只能选一个标签 | 不建单，追问申请人 |
| R4 | 同一批政策中两条用户数相同，提示可能选重了标签 | 建单，汇报中标黄提醒 |
| R5 | 必填字段有缺失或理解不确定 | 不建单，追问申请人 |
| R6 | 赠送节目包能找到对应的附属包 | 不建单，汇报原因 |

**原则：拿不准就不建。** 宁可多追问一次，也不建一条看起来正确、实际猜错了的单据，因为这类错误在审批时很难发现。

### 6.4 建单

| 编号 | 需求 | 优先级 |
|---|---|---|
| F4.1 | 通过明道云接口新建单据，进入现有审批流程 | P0 |
| F4.2 | 单据上标记「机器人创建」，便于审批人识别和后续统计 | P0 |
| F4.3 | 同一封邮件的多条政策批量创建 | P0 |

### 6.5 群内汇报

每封邮件处理完，在群里发一张卡片，内容包括：

- 邮件来源：国家、申请人、邮件标题
- 已建单：条数，每条的明道云链接
- 自动调整：如「生效日期 16 号已顺延到 19 号」
- 未建单：哪几条、原因、需要谁补什么
- 提醒项：如 R4 疑似重复标签

### 6.6 自我修正

| 层级 | 触发 | 机器人的动作 | 防护 |
|---|---|---|---|
| 规则层（提示词、规则文件） | 群里有人指出错误，如「赞比亚 Basic 赠送包应该选 xxx」 | 修改规则，立即生效 | 群内通知改了什么、依据哪句话、影响哪类政策 |
| 代码层 | 程序报错，或规则层解决不了 | 调用 AI 编程工具修改代码 | 先跑历史样例测试，全部通过才部署；不通过就不上线并报告 |
| 兜底 | — | 每次修改保留版本 | 群里说「回滚」即退回上一版 |

## 7. 不在第一期范围

- BOSS 中的政策优先级配置（另一个系统，需先确认是否有接口）
- 改用表单收集申请
- 邮件的存档整理（原来按大区 / 国家 / 日期存放的目录）

## 8. 非功能需求

| 项 | 要求 |
|---|---|
| 运行方式 | 部署在用户的云服务器上，常驻运行；飞书用长连接模式接收消息，不需要公网地址和域名 |
| AI 调用 | 解析邮件、自我修正都调用 Claude API；服务器只负责收消息、存数据、调接口 |
| 代码管理 | 代码放在服务器的 git 仓库中，每次自我修改都是一次提交，回滚即退回上一次提交 |
| 响应时间 | 邮件到达到群内汇报，5 分钟以内 |
| 日志 | 记录每封邮件的处理过程：解析结果、校验结果、建单结果、错误信息，用于排查问题 |
| 密钥管理 | 飞书 App ID / Secret、明道云 AppKey / Sign 存放在运行机器的配置文件中，不写进代码、不发到聊天里 |
| 权限 | 机器人只有明道云政策表的新建权限，没有审批和删除权限 |
