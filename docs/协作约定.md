# 协作约定

本仓所有代理（Claude、Codex、机器人自身）和产品负责人创建或编辑 Issue、PR 时，按本文执行。本文是本仓协作规范的唯一正文，其他文档通过链接引用。

## GitHub 写入规范

### Issue 标题字段

标题以一个方括号字段开头：

| 字段 | 用途 | 类型标签 |
| --- | --- | --- |
| `[feature]` | 交付用户或管理员可见能力的实现项 | `变更` |
| `[task]` | 工程内部工作：基建、迁移、门禁、配置 | `变更`；不改变产品承诺的维护用 `维护` |
| `[bug]` | 当前行为与已批准规格不一致的缺陷 | `缺陷` |
| `[epic]` | 一组 Story 共同形成的可独立验收结果 | `变更` |
| `[story]` | 用户、管理员或系统可观察到的一段完整价值 | `变更` |
| `[research]` | 调研与核实，产出结论不产出代码 | `研究` |
| `[decision]` | 请产品负责人决策的请求 | 按其性质取类型标签 |
| `[ops]` | 服务器部署与运维操作 | `ops` |
| `[tracking]` | 跟踪一个 Execution Trace，可纳入多个 Epic；实际工作单独建卡 | 无（不进状态链） |
| `[template]` | 长期保持打开、供代理复制使用的模板 | `长期参考` |

### 建卡必填字段

**所有工作项共同必填**

- 一个类型标签、一个状态标签、一个优先级标签。
- 要解决的问题与预期结果。
- 范围与非范围。
- 可观察的完成标准：用户、管理员或验证者怎样确认完成，不只写技术任务。执行方能自行完成的验证必须写成关卡条件；确实只有真人能做的步骤单列为「需 PM 配合」并说明原因。
- 关闭前若改变长期产品事实，先更新 `docs/`；否则写明「无需回写」的原因。
- 不记录凭据、个人数据、邮件原文或敏感配置（本仓公开）。

**按类型追加**

| 类型 | 追加字段 |
| --- | --- |
| `[feature]`／`[story]`／`[task]`／`[epic]` | 正文第一个区块是 `TO PM`（字段见下）；关联的产品文档章节；相关 Issue／PR 与阻塞关系 |
| `[bug]` | 期望行为；实际行为、影响与复现步骤；脱敏证据（日志、截图、时间） |
| `[research]` | 要回答的问题及它支持哪项判断；范围与方法；什么证据能回答问题，无法得到结论时怎样记录 |
| `[decision]` | 需要确认的决定；逐个候选方案及其对用户体验、外部依赖、安全、成本、可逆性的影响；不决策时哪些实现被阻塞 |

**`TO PM` 字段**：应用后得到什么／不应用的代价／代码变动面（约 N 个文件，是否引入新概念或新常驻进程）／架构变动（接口、数据存储）／谁会调用它／依赖怎么装上／测试与部署成本／可逆性／需要产品负责人拍板的（没有则写「无，按下述范围直接实施」）。

- 只写可核对的事实和变动面，不替产品负责人写「复杂度可控」等判断；事实不足时写「未知」和原因。
- 「谁会调用它」和「依赖怎么装上」是开工事实。确无调用方时写明本次只交付组件，确无新增依赖时写「无」；任一项答不出就不开工。
- 小型、可逆且不改变用户体验、权限、数据或外部依赖边界的改动可直接实施；其他变更在编码前建卡。

### 标签清单

新增、改名或删除标签先改仓库再改本表。GitHub 默认标签已删除，仓库只保留下表标签。

**类型标签（恰好一个，工作项必带）**

| 标签 | 含义 |
| --- | --- |
| `变更` | 需要产品或实现变更的工作（[feature]/[story]/[task]/[epic]） |
| `缺陷` | 当前行为与已批准规格不一致 |
| `研究` | 有明确结论和结束条件的调查 |
| `维护` | 不改变产品承诺的维护工作 |
| `ops` | 服务器部署与运维操作的说明与执行 |

**状态标签（工作项恰好一个）**

| 标签 | 含义 |
| --- | --- |
| `待分诊` | 刚提交，内容与事实尚未核实；状态链第一环，不可施工 |
| `pre-ready` | 范围与验收目标已确认，但前置未完成；不可施工 |
| `Ready` | 已符合要求，可进入施工 |
| `执行中` | 已领取且正在实施 |
| `待验收` | 实现与自测完成，约定验收尚未完成 |
| `观察中` | 必要验收通过，已上线持续观察；须记录负责人、窗口、指标及退出标准 |
| `阻塞` | 因依赖、决策或冲突无法继续 |
| `待决策` | 等待产品负责人确认的阻塞性选择 |

**非工作项与 PR 标签**

| 标签 | 含义 |
| --- | --- |
| `长期参考` | 长期保持开放的模板或研究快照；不进入研发队列 |
| `待审查` | PR 专用：等待审查；不作为 Issue 主状态 |
| `机器人自改` | PR 专用：机器人根据群内纠错自动生成的修改 |

**优先级标签（工作项恰好一个，`长期参考` 不打）**

| 标签 | 含义 |
| --- | --- |
| `P0` | 最高优先级：阻塞其他工作或有硬期限 |
| `P1` | 正常优先级：计划内工作，按序推进 |
| `P2` | 较低优先级：可延后，不阻塞任何人 |

**风险标签（按需，可多个）**

| 标签 | 含义 |
| --- | --- |
| `权限风险` | 涉及身份、授权或数据范围 |
| `外部依赖风险` | 涉及飞书、明道云、邮箱、BOSS、Claude API 等外部系统约束 |
| `安全风险` | 涉及安全边界或敏感信息 |

### 状态链

| 类别 | 状态链 |
| --- | --- |
| 工作项（`[feature]`、`[task]`、`[bug]`、`[epic]`、`[story]`、`[research]`、`[decision]`、`[ops]`） | 开放时恰好一个状态标签。`待分诊 → pre-ready → Ready → 执行中 → 待验收 → 观察中 → closed`。无需观察可由 `待验收` 直接关闭；等待前置或裁定时用 `阻塞`／`待决策` |
| `[tracking]` | 不进状态链；执行进度记在 Trace 任务表 |
| `[template]` 与其他 `长期参考` | 不进状态链；`长期参考` 与状态标签互斥 |

- 新建默认 `待分诊`；范围与验收目标确认后才 `pre-ready`，前置齐备才 `Ready`。
- 只能从 `Ready` 领取。领取时换 `执行中`，留言写明执行者和领取有效期（UTC 截止时刻）。到期未交回结果，由 Trace 编排者回收；无 Trace 时由 Issue 创建者回收。回收时改回 `pre-ready` 并留言记录原因。
- 转 `待验收` 前，实施和自测须完成（研究项须已有结果）。在 Issue 记录交付物或 PR、已完成的自测及证据指针、待验收项和验收负责人。
- 必要验收通过，且已在明确环境和固定版本开始观察后，才转 `观察中`。在 Issue 记录环境、版本、负责人、开始时间、截止时间或样本量、检查指标、失败条件、失败后的处置和关闭标准。
- 验收或观察失败、工作项被退回时，改回 `pre-ready`，在 Issue 留下失败证据或退回理由及需补齐的前置条件。
- 完成标准全部成立且已按建卡要求回写后关闭，关闭时移除状态标签。

### 优先级、依赖与里程碑

- 先后顺序用 GitHub 原生关系表达：被阻塞用 `gh issue edit N --add-blocked-by M`，整体与部分用 `gh issue edit N --add-sub-issue M`。只登记正文写明的依赖。
- 版本用 GitHub Milestone 表达。`P0`／`P1` 必须归入一个里程碑；`P2` 可在进入排期时再归入。里程碑归属与 `Ready` 的前置条件分别判断。
- 对应版本发版后关闭里程碑。先将未完成的 Issue 移出；已确定后续版本的，移入对应里程碑。在 Issue 留言说明移出的原因和后续归属。

### 提交与披露

- Issue、PR 正文或评论用含真实换行的 Markdown 文件，通过 `--body-file` 提交；提交后立即读回核对格式。
- 委派子代理起草 Issue、PR、评论或提交说明时，在派发卡标注「将写入 GitHub」。由主代理在写入前做最小披露复核，写入后读回核对内容与格式。
- 本仓公开：写入前做最小披露复核，不写凭据、本机路径、服务器地址、用户数据、邮件原文。

## PR 规则

**分支与范围**

- 所有改动走功能分支和 PR，禁止直接写 `main`。分支名 `<类别>/<Issue号>-<短名>`，类别取 `feat`、`fix`、`docs`、`chore`、`release`，例如 `feat/3-mail-reader`。
- 一个 PR 只解决一个 Issue。顺手发现的问题另开 Issue，不夹带。

**标题与正文**

- 标题：一句中文说清改了什么，末尾括注 Issue 号。
- 正文按 [PR 模板](../.github/pull_request_template.md)：目标、实际差异、证据、未验证、回退方式。
- 关联 Issue 一律写 `Refs #N`，不用 `Closes`/`Fixes` 自动关单：合并 PR 不等于验收通过。

**审查（按风险分档）**

| 改动类型 | 合并前审查 |
| --- | --- |
| 纯文档、机械调整（不改代码、配置、CI） | 作者自查即可，PR 里写明「同源自查」 |
| 代码、脚本、配置、CI | 至少一名未参与实现的审核者（独立子代理或 Codex），结论贴在 PR 评论 |
| 凭据、权限、明道云写入范围的改动 | 两家独立审核（如 Claude 子代理 + Codex） |
| 机器人自改（`机器人自改` 标签） | 由历史样例测试把关，测试通过即可合并（产品决策 D4：直接生效） |
| Trace 批次 | 按当期 Trace 合同的角色表执行合并前审查，逐条处置意见 |

审查发现先处置（修复，或写明不修的理由）再合并；候选提交变了，旧结论失效，只对变化部分做定向复核。仅同步 `main` 且符合下文「PR 推送纪律」第 5 条时，可沿用本地审核结论。

**合并**

- `qianshu-checks` 通过后用 `gh pr merge <PR号> --merge` 合并（合并提交，不压缩、不变基）。
- 合并后远端分支由 GitHub 自动删除；本地分支自行清理。

### PR 推送纪律

1. **本地定稿才推送**。施工、快检、内审和修复都在本地完成。快检与 CI 使用同一套检查，高风险卡另加本机 Codex 审核。适用检查和审核全部通过才算定稿。
2. **不开草稿 PR**。定稿后一次推送，直接开正式 PR，CI 与云端审核并行。
3. **问题攒齐一次修**。把 CI、云端审核和本地两层审核的发现汇总成一张缺陷清单，一次修完、一次推送。每个 PR 开出后通常最多推送两次，第三次推送前须先报告守望者。
4. **合并串行**。一次只推进一个 PR 到合并，轮到该 PR 时才同步 `main`，审完立即由守望者合并。合同 PR（含修订 PR）的合并人按「Execution Trace」节执行。
5. **仅同步 `main` 的推送可沿用本地审核结论**。推送只同步 `main`、未改动本 PR 文件，且云端审核没有新增 P0 / P1 时，沿用原结论，无需重做本地两层审核。涉及 `src/qianshu/mingdao/`、依赖或配置的改动不适用此例外。

## 仓库保护

服务端规则（GitHub Rulesets，网页：仓库 Settings → Rules）：

| 规则集 | 保护对象 | 内容 |
| --- | --- | --- |
| `main-required-ci` | 默认分支 `main` | 禁止删除、禁止强推；必须经 PR 合并（不要求人工批准）；必过检查 `qianshu-checks`，且 PR 须包含最新 `main` |
| `v-tags-immutable` | `v*` 标签 | 已发布的版本标签不得改动或删除 |

## CI 资源约定

目标：尽量少用 GitHub Actions 资源。

- **只有一个工作流、一个任务**：`.github/workflows/checks.yml` 的 `qianshu-checks`，它就是 `main` 的必过检查。不另加工作流；确需新增，先建 Issue 说明为什么不能并进现有任务。
- **只在正式 PR 上自动跑**：不在 push 到 `main`、定时任务、草稿 PR 上跑。`main` 只能通过 PR 改动，PR 上已经检查过，合并后不重复检查。
- **按改动范围选档**：`qianshu-checks` 的文档档与完整档见[验证与门禁](验证与门禁.md#门禁档位)。
- **新提交取消旧运行**：同一 PR 推了新提交，正在跑的旧运行自动取消。
- **不上传产物**：不使用 `upload-artifact`，避免占用存储。
- **超时 10 分钟**：防止卡住的任务一直计时。
- **不做自动部署**：部署在用户自己的服务器上完成（服务器拉取 `main`），不通过 Actions。
- **外部贡献者的 PR 需要手动批准才跑**：防止公开仓库被他人的 PR 消耗资源。
- 计费说明：公开仓库使用 GitHub 托管的标准运行机不计分钟数。上面这些约定在仓库转为私有时同样适用。

## Execution Trace

多批次工作按 [trace-kit `METHOD.md` v27](https://github.com/Moshuiwang/trace-kit/blob/v0.10.0/METHOD.md) 组织。[Trace 索引](traces/README.md)登记各 Trace；在 `docs/traces/<Issue号>-<短名>/` 保存 `合同.md`、`任务表.md`、`验收.md`。

合同 PR（含修订 PR）由该合同「授权终点」写明的批准人合并，合并即批准该版合同。编排者不合并自己起草的合同 PR。角色与职责以该合同的授权终点和角色表为准。

本仓暂不采用本机 hook、合并脚本、发版产物工作流及仅允许 App 创建 `v*` 标签的规则。

自建运行机、`ci:hosted-fallback` 回退标签和 Codex 云端审核的接入见 [#14](https://github.com/Moshuiwang/qianshu/issues/14)。
